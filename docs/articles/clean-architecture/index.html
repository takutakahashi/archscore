Clean Architectureは、
何をきれいにするのか。

円を覚えるための記事ではありません。まず目的をつかみ、依存の向き、境界、実装へと少しずつ解像度を上げます。

先に結論

Clean Architectureが守ろうとするのは、ビジネス上の判断です。UI、DB、フレームワークの都合が、その判断へ流れ込まないように依存を整えます。

  1. なぜ必要か
  2. ひとつのルール
  3. 4つの領域
  4. 実装の道具
  5. どう測るか
1 / 5 — まず目的

変わりやすいものから、変えたくないものを守る。

注文を確定できる条件、料金の計算方法、ユーザーへ与える権限。こうしたルールは、プロダクトが価値を提供するための中心です。一方で、HTTPフレームワーク、データベース、メッセージブローカーは、そのルールを届けるための手段です。

問題は、手段の都合が中心へ入り込むことです。注文判定の関数がHTTPのRequestを受け取り、ORMのModelを直接更新し、特定クラウドのSDKで通知するなら、業務ルールを理解するために3つの技術を同時に理解しなければなりません。

「きれい」とは、見た目ではなく変更の伝わり方

ディレクトリが左右対称でも、ファイル名が揃っていても、技術変更が業務ルールまで波及するなら目的を果たしていません。Clean Architectureでいうcleanは、変更理由の異なるものを分け、外側の変更を内側へ伝えない状態だと捉えると理解しやすくなります。

2 / 5 — 全体を貫くルール

ソースコードの依存は、内側だけを向く。

Clean Architectureの中心はDependency Ruleです。内側にはプロダクト固有のポリシー、外側には技術的な詳細を置きます。外側は内側を知ってよいが、内側は外側を知りません。

技術へ依存するOrderService → PostgresOrderStore

DBを変えると、注文処理も変更対象になる。

契約を内側に置くPostgresStore → OrderRepository ← PlaceOrder

Use Caseが必要な契約を定義し、DB側が実装する。

実行時の呼び出しと、ソース依存は別

実行時にはUse CaseがRepositoryを呼びます。それでもソース上では、Use Caseが定義したinterfaceを外側のRepository実装が満たします。呼び出しの流れではなく、コンパイル時に誰が誰の名前を知るかを逆転させています。

中心のルールは、外側の製品名やフレームワーク型を知らなくてよい。

3 / 5 — 地図を読む

4つの領域は、役割を考えるための地図。

よく見る同心円は、必須のディレクトリ構成ではありません。内側へ行くほどプロダクト固有で、外側へ行くほど交換可能な詳細になる、という距離感を示します。

中心

Entities

複数のユースケースから使われる、長期的なビジネスルール。注文、契約、在庫などの概念と不変条件。

内側

Use Cases

ユーザーの目的を完遂する手順。「注文を確定する」「権限を付与する」といったアプリケーション固有の判断。

境界

Interface Adapters

外部のデータ形式と、Use Caseが扱う形式を変換する。Controller、Presenter、Repository実装など。

外側

Frameworks & Drivers

Web、DB、UI、デバイス、クラウドSDK。価値を届けるために必要だが、交換可能にしたい詳細。

4層に分ければ正しい、ではない

小さなCRUDサービスなら、EntityとUse Caseを分けても同じ理由で同時に変わるだけかもしれません。層の数は目的ではなく、異なる変更理由を表現した結果です。

4 / 5 — 実装へ降りる

境界を作る道具は、3つあればよい。

01

Port

内側が外部へ期待する契約。外部技術の語彙を内側へ漏らさない。

type OrderRepository interface { Save(Order) error }
02

Adapter

HTTP、DB、CLIなどの形式をPortへ合わせ、技術変更を受け止める。

type PostgresOrders struct { db *sql.DB }
03

Composition root

具体的な実装を選び組み立てる場所。再利用される業務コードは混ぜない。

usecase := NewPlaceOrder(PostgresOrders{db})

interfaceは、境界がある場所にだけ置く

すべてのstructへ1対1のinterfaceを作っても、変更理由は分離されません。内側のポリシーから外側の詳細を隠す必要があるときにPortを置きます。

5 / 5 — 観測する

守れているかは、依存グラフで確かめられる。

どのモジュールがどこへ依存してよいかを宣言すれば、Dependency Ruleの一部は機械的に検証できます。

守りたいことarchscoreで見るもの
依存は内側へ向くmayDependOn
実装詳細を隠すpublicPaths
公開契約を増やしすぎないmaxPublicSymbols
組み立てを端へ置くcomposition-root
相互依存を作らないacyclicity
変更を境界内へ閉じるchange locality
ツールが判断できないこと

Domainという名前のパッケージに、本当に業務ルールがあるか。境界が実際の変更理由に沿っているか。archscoreは宣言と実装の一致を見ますが、宣言そのものの意味は人が判断します。

まとめ

円ではなく、変更の矢印を見る。

まず「ビジネス上の判断を技術詳細から守る」という目的を置く。次にソース依存を内側へ向け、必要な場所にだけPortとAdapterを作り、最後に依存グラフで確かめます。

この順なら、4層の名前を忘れても設計判断は残ります。
