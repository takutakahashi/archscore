良いアーキテクチャを、
どう観測するか。

最初から7つの指標を暗記しません。まず「何のために測るか」を置き、構造、変更コスト、履歴、確からしさの順に信号を重ねます。

先に結論

スコアは設計の正解ではありません。宣言した構造と実際のコードがずれ始めたことを、変更が難しくなる前に知らせる早期警報です。

この記事の流れ

  1. 測る目的
  2. 構造の安全性
  3. 変更コスト
  4. 履歴の信号
  5. 確からしさ
1 / 5 — 目的を置く

点数を上げるためではなく、設計のずれに気づくため。

アーキテクチャは、ある時点の図ではなく、日々の変更が作る依存関係です。レビューで一度合意しても、新しいimport、便利な共通関数、急ぎの例外経路が少しずつ構造を変えます。

そこで、最初に「どのコードがどの境界に属し、どこへ依存してよいか」を宣言します。測定の役割は、その宣言を正解にすることではなく、実装との差分を見つけることです。

良さを直接測るのではなく、良さを壊す兆候を観測する。

2 / 5 — まず壊れ方を見る

最初の3信号は、構造が読める状態かを確かめる。

30点

境界

許可していない依存と、公開契約を迂回する参照。設計意図とコードのずれを直接見る。

20点

非循環性

AがBを、BがAを知る状態。変更順序と責任の向きが決められなくなる。

10点

網羅率

どの境界にも属さないコード。未分類が多ければ、他の構造評価も信用できない。

この3つは、設計が良いかを断定する前提条件です。特に境界違反と循環は、合計点が高くても独立してゲートを失敗させます。平均点で重大な構造破壊を隠さないためです。

3 / 5 — 変更コストへ近づく

次の3信号は、変更がどこまで波及するかを見る。

10点

公開契約

外部が知ってよい入口とシンボル数。公開面は、将来守り続ける約束の面積になる。

15点

結合度

依存先数だけでなく、その依存先の不安定さを加味する。揺れる機能への依存は負荷が高い。

10点

凝集度

解決できた依存のうち境界内に留まる割合。関連する責務が一緒に置かれているかの代理信号。

いずれも意味そのものは測れません。公開シンボルが少なくても契約が悪いことはあり、内部依存が多くても責務が混在することはあります。数値は、詳しく読む場所を選ぶために使います。

4 / 5 — 時間を加える

静的な図に、実際の変更履歴を重ねる。

importがなくても、DB migrationとモデル、APIとSDKのように、同じ要求で一緒に変わり続けるコードがあります。変更局所性は、ある境界に関係するコミットの変更が、その境界内へ収まった割合を見ます。

局所的な変更feature A: [module-a, module-a]

境界が変更理由を閉じ込めている。

拡散する変更feature A: [a, b, c, shared]

境界をまたぐ理由を調べる候補。

共変更は因果関係ではありません。大規模リネームやフォーマット変更でも一緒に変わります。だから履歴不足は失点にせず、「まだ分からない」と扱います。

5 / 5 — 数字の読み方

100点と、100%確かであることを分ける。

観測できた75点分がすべて良好なら、観測スコアは100です。しかし残り25点分の証拠はありません。archscoreはこれを、score 100、confidence 75%、lower bound 75、upper bound 100として分けます。

スコアを読む順番

まず gate、次に analysis coverage と confidence、その後で score と各componentを見る。単一の総合点だけを比較しない。

まとめ

構造、コスト、時間、確信度の順に読む。

7指標は同列のチェックリストではありません。構造が読めるかを確かめ、変更の波及を見て、履歴を重ね、最後に証拠の確からしさを確認する。段階で読むと、点数が設計判断の代わりになりません。
