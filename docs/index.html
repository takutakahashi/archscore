ファイルを「処理の順番」で分けると、変更が境界を貫通する。

一言でいうと、モジュールは実行ステップではなく、将来変わりうる設計判断の周りに作る。

論文が置いた問題

Parnas は、同じ KWIC（文中の語を循環シフトして索引を作る）システムを2通りに分解します。一方は「入力する → シフトする → 並べ替える → 出力する」という処理手順ごとの分割。もう一方は、データ表現、シフトの生成方法、並べ替え方など、外から隠したい設計判断ごとの分割です。

正常系だけを見れば、前者のほうがフローを追いやすく見えます。差が出るのは変更時です。入力形式、保存形式、シフト生成のタイミング、並べ替えアルゴリズムを変えるとき、処理手順で切った構造では複数モジュールへ知識が漏れています。設計判断で切った構造なら、その判断を所有するモジュール内に変更を閉じ込められます。

「情報隠蔽」はアクセス修飾子の話ではない

private を付けることは手段のひとつですが、中心は「ほかのモジュールが何を知らずに済むか」です。DBのテーブル構造を直接参照できなくても、十数個の用途別メソッドがスキーマの都合を露出していれば、設計判断は隠れていません。逆に公開APIが多少広くても、変化しやすい実装上の選択を安定した語彙へ変換できていれば、隠蔽は機能しています。

処理で分けるload → normalize → save

保存形式の知識が各段階へ漏れやすい

判断で分けるDocumentStore.save(doc)

保存形式を Store の後ろへ閉じ込める

publicPaths は、ある境界の外側が知ってよい入口を宣言します。private dependency 違反は、別モジュールが隠されるべき実装詳細を知ってしまった場所です。mayDependOn は、その知識が流れてよい方向を宣言します。ただし、境界の名前や切り方が良いかまでは静的依存だけで判定できません。そこは変更履歴と人間の設計判断が必要です。

この論文からは言えないこと

「モジュールは小さいほど良い」「公開シンボルは10個以下が正しい」とは述べていません。情報隠蔽は分割基準であり、archscore のシンボル上限や配点は、その基準を運用可能にするローカルポリシーです。

[2] Stevens, Myers & Constantine, 1974

依存の本数だけでなく、何を共有しているかが変更コストを決める。

一言でいうと、モジュール間の結びつきは弱く、モジュール内の要素はひとつの目的へ強く関係しているほうが扱いやすい。

coupling と cohesion は別の軸

結合度（coupling）は、モジュール同士がどれほど互いの事情に依存するかです。呼び出しが1本でも、グローバルな状態や相手の内部表現を共有していれば強く結びつきます。反対に呼び出しが複数あっても、安定した値オブジェクトと小さな契約だけを介するなら、影響は限定できます。

凝集度（cohesion）は、ひとつのモジュールに入っている要素が、同じ責務を果たすためにどれほど関係しているかです。「ユーザー関連」という名前だけで認証、請求、通知を集めたモジュールは、語彙上はまとまっていても変更理由は別です。ひとつのユースケースを完遂するためにデータと処理が集まっていれば、変更理由も揃いやすくなります。

低結合・高凝集は、行数を減らす標語ではない

狙いは局所的に推論できる範囲を作ることです。ある変更を理解するために、別チームのモジュールの内部状態、呼び出し順、暗黙の初期化まで頭へ載せる必要があるなら結合は強い。ひとつのモジュールを変更するたび無関係なテスト群が壊れるなら、凝集は疑わしい。この2軸は、開発者が同時に覚える必要のある文脈の量として現れます。

コードレビューでの兆候

「このフィールドは先に別APIで初期化済みのはず」「この enum を増やすと3サービスを同時デプロイする」が頻出するなら、import数には出ない強い結合がある。

archscore が見ているもの

fanOut は直接依存先の数、couplingLoad は依存先の不安定さを加味した負荷です。安定した共通基盤1つへの依存と、変更頻度の高い機能5つへの依存を同一視しません。凝集度は解決できた依存のうち境界内に留まる割合で近似します。ただし、Goの単一パッケージのように内部importが存在しない構造では証拠がないため、満点ではなく未評価になります。

この論文からは言えないこと

依存ゼロを目指すべき、という話ではありません。役割を果たすには依存が必要です。また、構造上の内部エッジ比率は意味的な凝集そのものではなく、代理信号です。

[3] Murphy, Notkin & Sullivan, 2001

アーキテクチャ図を正解にせず、実装との差分を会話の材料にする。

一言でいうと、設計者の高水準モデルとソースから抽出した依存を対応づけ、一致・不一致・欠落として要約する。

Reflexion Model の3つの入力

必要なのは、設計者が期待するモジュールと依存を表す高水準モデル、ソースから抽出した関係を持つソースモデル、そしてソースの要素がどの高水準モジュールに属するかを示す写像です。この写像を通して2つを比較すると、期待どおり存在する関係（convergence）、実装にだけある関係（divergence）、設計上はあるが実装に見つからない関係（absence）が得られます。

大事なのは、不一致を即座に「コードの誤り」と決めないことです。設計モデルが古い、写像が粗い、生成コードを含めた、あるいは実装が意図せず逸脱した。差分は、どちらを直すべきか調査する入口です。

完全なモデルより、目的に十分なモデル

この手法は、すべてのクラスと呼び出しを精密に図示することを目指しません。今の作業で検証したい仮説に合わせて高水準モデルと写像を作り、差分を見て反復します。巨大なExcelコードベースにも適用された背景には、詳細を捨てて関係を要約するからこそ、人が推論できるという考えがあります。

期待する依存＋ソースの依存＋所属の写像＝意味のある差分

archscore が見ているもの

archscore.json が高水準モデル、import解析がソースモデル、paths が写像に相当します。許可していない依存は divergence として具体的なファイル・行まで降ろします。analysisCoverage は写像できなかったソースの割合を表し、未割り当てコードが多いほど、ほかの構造指標の信頼度も下げます。

ただし archscore は、許可した依存が実際には存在しないことを違反にしません。mayDependOn は「必須」ではなく「許可」だからです。この点は原典の absence と意図的に異なります。

この論文からは言えないこと

宣言モデルが自動的に正しいとは限りません。ポリシーに実装を無理やり合わせれば、古い設計を固定化します。観測モードと差分レビューが必要なのはそのためです。

[4] Sarkar, Kak & Rama, 2008

クラスがきれいでも、パッケージの切り方が良いとは限らない。

一言でいうと、大規模システムではクラスより上のモジュール粒度と、その公開API・モジュール間依存を独立して評価する必要がある。

クラスとモジュールを同一視しない

従来のオブジェクト指向メトリクスは、クラスをモジュールのように扱うことが多くありました。しかし数百万行のシステムでは、開発者が日常的に扱う境界はパッケージ、サブシステム、コンポーネントです。個々のクラスがカプセル化されていても、パッケージをまたぐ継承、関連、メソッド呼び出し、状態へのアクセスが網の目になれば、保守と拡張は難しくなります。

この論文は、モジュールの公開APIとモジュール間依存の両面を見るメトリクス群を提示します。つまり「内部がきれいか」だけでなく、「外部へどれだけの面積を見せ、どんな関係を作ったか」を評価対象に引き上げました。

公開面積は、将来守り続ける約束の量

公開された型や関数は、単なるコード量ではありません。利用側が依存できる選択肢であり、変更時に互換性を考慮する範囲です。APIが大きいほど必ず悪いわけではありませんが、内部の都合が公開面へ流出していないか、複数の入口が同じ責務を重複して表現していないかを問う必要があります。

設計レビューでの問い

この公開型は利用者の問題領域を表しているか。それとも、内部フレームワーク・永続化形式・実装順序を利用者へ覚えさせているか。

archscore が見ているもの

publicPaths と maxPublicSymbols は公開面を明示し、その大きさを追います。契約を実際に利用する inbound 関係で重みづけするため、誰からも参照されないleaf moduleが、重要な契約の評価を薄めません。fan-in / fan-out、private dependency、cohesion と組み合わせ、単一の数字へ早急に潰さない点もこの問題設定に沿っています。

この論文からは言えないこと

APIシンボル数だけでモジュール化品質を決められるわけではありません。archscore も型レベルの全表面、意味の重複、実行時結合までは測れません。数値はレビュー対象を絞るための入口です。

[5] Gall, Hajek & Jazayeri, 1998

import がなくても、一緒に変わり続けるなら依存しているかもしれない。

一言でいうと、リリース履歴の共変更パターンから、ソース構造だけでは見えない論理的結合を発見する。

静的依存が見落とすもの

APIとクライアント、DB migrationとモデル、設定スキーマとパーサー、サーバーとSDK。これらは同じ言語の import graph に現れないことがあります。それでも同じ要求のたびに一緒に変更されるなら、開発上は結びついています。論文は大規模な通信交換システムの20リリースを調べ、プログラム、モジュール、サブシステムのバージョン番号と変更報告を使って共通の変更パターンを探しました。

これを論理的結合と呼ぶのは、構文上の参照ではなく、変更理由を共有している可能性があるからです。意図した協調変更かもしれないし、責務が誤った境界に分かれている兆候かもしれません。

共変更は因果関係ではない

大規模リネーム、ライセンス更新、フォーマッタ導入、release branchの運用でも大量のファイルが一緒に変わります。履歴が短い、コミットが巨大、squash方針が不統一なら信号は歪みます。したがって、共変更は「この境界は間違い」という判定ではなく、「静的構造では説明できない関係を調べる」ための候補生成です。

境界発見では、静的依存 50%、Git co-change の Jaccard 類似度 40%、パス語彙 10%を組み合わせます。最低3回の共変更を要求し、偶然の一致を弱めます。変更局所性では、あるモジュールに関係するコミットのうち、解析対象変更の80%以上がそのモジュール内に収まる割合を測ります。履歴不足は失点ではなく、低い信頼度として扱います。

この論文からは言えないこと

一緒に変わるコードを必ず同じモジュールへ移すべき、とは言えません。プロトコルの両端のように、分離したまま協調変更するのが正しい場合もあります。履歴は境界を決める証拠のひとつです。
